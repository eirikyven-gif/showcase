## Explicit safety substitutions

- Source archive and exact SHA/tree are recorded above. `showcase` baseline `b5e117cfe6d08f94ed9128523a854218b9d03009` had no route/catalog entry; route name was not used to infer lineage.
- No real login, account/session identity, server capability enforcement, server/account/database persistence, private people records, private API/services, secrets, actual email delivery, public bearer share links/tokens, or uploaded/private file bytes/media. All example records are synthetic. Simulated capability choices gate local controls only.
- The only persistent browser state is the source-compatible `hu_inv_view_mode` display preference; all business records reset on reload.
- Plan-only features absent from executable UI (bulk actions, partial returns, pricing workflows, share filters/revoke, item deletion) are not represented as source parity.

## Remaining gaps, each security-blocked

- WordPress login, authenticated identity/session, actual WordPress capability enforcement, setup warnings and server flash/redirect behavior. The local role/capability selector and UI gating are a non-security simulation; no login or role record exists.
- Durable server/database state and real account/business records; example changes live only in page memory.
- The source upload action is represented by choosing a bundled synthetic fixture and creating/removing metadata; actual file selection, uploads, binary attachments, private media URLs, and opening source files are disabled. Local view shows generated illustration/text only.
- The source share-link action is represented by creating/listing a synthetic row, opening a tokenless same-page preview, and copying its route. No public endpoint, generated bearer token, per-link content selection/access control, or expiry-enforced share is created; optional email is not sent.
- Real contact/person values; contact records and the mailto destination use synthetic values and the reserved `.invalid` domain.

These blocks remove security or external-service behavior while preserving local screens, fields, and workflows where possible. Final comparison against the pinned runnable UI, forms, repository validation, and action classes found no additional source gaps beyond these listed blocks. They remain material user-facing parity gaps. PR #90 stays draft; Issue #2 is partially addressed. Do not mark ready, merge, or deploy while these blocks remain unresolved.

## Parity gate and QA

Source comparison found and corrected one form gap: source add/edit permits category, location, and status to be unset, while the previous demo forced one of each. The portal and admin forms now expose the source blank choice; the admin form leaves category unset because the source admin form does not expose a category field. Chromium validation also found and fixed a date-error path that attempted `reportValidity()` on a container rather than the date inputs. Source SKU rules are now reproduced: blank SKU on item creation generates a unique `AUTO-…` value, while edit requires a nonempty unique SKU. Custom fields sort by configured order, inactive values stay hidden in item detail, and key validation/uniqueness, the 64-character limit, default order 0, and rename behavior follow the pinned repository. Renaming a key does not migrate its values, matching source behavior. Regression assertions cover these corrections.

Chromium QA at 390px and 1440px exercised all six portal tabs, no-result inventory search, item creation with blank source options and generated SKU, invalid rental-date rejection, required stock-count reason, local share-row simulation, and admin item blank status/location. Both sizes had no horizontal overflow, JavaScript errors, or off-origin requests; keyboard focus rings were visible and admin input labels were associated. Additional 390px custom-field QA verified duplicate-key, invalid-character and >64-character rejection, configured ordering, and source-compatible key rename behavior. Earlier workflow QA on this route also covered edit/detail, instances, notes and attachment references, contacts, rental changes/activation/return, CSV duplicate handling, XLSX export, reports, and admin settings. Only explicitly listed safety blocks remain; the PR stays draft while they remain unresolved. Automated checks and CI results are tracked in the PR body.

## Focused WCAG 2.1 AA accessibility audit

A route-wide Chromium audit covered the six portal panels, three local admin screens, inventory detail, and the editor dialog. Interactive controls had accessible names or associated labels throughout; empty action-table headers now expose “Handlinger”, column headers declare their scope, and repetitive edit/delete controls include the affected setting or field name. Portal tabs implement one roving Tab stop, Left/Right plus Home/End selection, and an associated labelled tab panel. Re-rendered actions and admin return restore focus. The native editor dialog is named by its heading, receives initial focus, bounds Tab and Shift+Tab at both ends, and restores the invoking control immediately on Escape, cancel, and save.

Focus indicators use a 3px `#005fcc` outline (contrast 5.98:1 on white, 5.55:1 on the page wash). Normal-size muted text is `#596a60` (5.33:1 on the page wash, 5.75:1 on white); the main text color exceeds 4.5:1. Browser contrast sampling found no normal-text failures in the portal panels. Flexible form, summary, settings, and admin layouts now reflow at narrow widths; data tables and the tab strip retain their own horizontal scrolling where needed.

Chromium reflow QA passed with no page-level horizontal overflow at 320, 390, 768, and 1440 CSS px, including the new role selector, all six tabs and capability settings. The role selector initially expanded the 320px page; its responsive width was constrained and the repeat check passed. For a 200% zoom-equivalent check, the effective CSS viewport was halved to 160, 195, 384, and 720 px; every portal panel and admin screen again had no page-level overflow. Keyboard checks verified arrow/Home/End tab behavior, visible focus, twelve successive Tab presses and six reverse presses contained within the modal, immediate focus return after Escape and save, and zero unnamed enabled controls. The checked run reported no JavaScript errors and no off-origin requests. The local server and Chromium processes were closed after the run. Regression assertions are in `tests/wp-varelager-accessibility.test.mjs`.

Synthetic-workflow Chromium QA exercised reader/visitor/administrator gating; create/list/copy/open/back for a share route; image and document fixture selection, list, view and image metadata deletion; clipboard contents contained only `#share-preview` with no token. No JavaScript errors or off-origin requests occurred. Focused tests pass (10/10); `node --check` and `git diff --check` pass. Vibe static validation run #329 passed for commit `9588f107f54de8e497529dc84dda33650e5ced95`. Browser and local server launched for this run were closed.

The tested accessibility scope has no remaining known AA blocker. The local substitutes now cover capability selection/gating, share-list preview/copy, and synthetic attachment selection/list/view/delete. Actual identity, durable persistence, real people, file bytes/private media, public bearer links, and email remain explicitly disabled; PR #90 remains draft while source parity is reviewed.
